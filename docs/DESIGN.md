## 1. 页面组织

```text
设置 → 模组设置 → PreLuna
  ├─ 概览
  ├─ 已接入 MOD
  │    └─ 某个已安装 MOD
  │         ├─ 当前状态与限制
  │         ├─ 设置分组（具体项待选）
  │         └─ 页面操作与结果
  └─ 状态与诊断
```

使用原生分组／子菜单表达上述信息结构，不要求 TheArchive 具备自定义标签页或额外弹窗。避免重复创建同一 MOD 的功能开关：这里的管理页面不能被理解为加载／卸载该 DLL 的按钮。

| 页面 | 展示与操作 |
| --- | --- |
| 概览 | 管理模块与框架版本、已接入数量、待处理草稿／待生效数量；引导进入对应模块，不集中罗列所有设置 |
| 已接入 MOD | 默认显示已安装且本仓已登记的目标；显示名称、版本、接入状态，按工作区中文功能排序；已知但未安装的目标可在“显示未安装模块”下查看，不提供下载安装按钮 |
| 单 MOD 详情 | 顶部显示能力和限制；中部按功能组织设置；底部显示本页操作、适用范围和上一次操作结果。原型只用少量分组，不增加多层空菜单 |
| 状态与诊断 | 模块／框架兼容状态、明确的不可用原因、最近操作结果与必要错误摘要；详细日志供开发者排查，不将方法名、堆栈和内部标识塞进正常设置流程 |

只管理显式登记目标，不自动把所有 BepInEx 插件和配置项扫描成可编辑页面。已安装但没有适配器、版本未经支持或初始化未完成时，只显示状态和原因；缺失模块不影响其他页面。第三方已有设置继续保留在原页面，不复制成第二套控制入口。

首版不新增全局快捷键，沿用原菜单的鼠标、焦点和输入接管。管理模块不尝试在多人游戏中额外暂停世界；页面打开期间是否仍有目标 MOD 热键生效需单独实测，不能靠菜单已显示推断输入已经隔离。

## 2. 用户可见状态

每项设置区分以下数据；内部按稳定键识别，不能以中文显示名称作为存储键：

| 数据 | 含义 | 生命周期／归属 |
| --- | --- | --- |
| 已保存值 P | 原 MOD 的持久配置，经原 MOD 解析后的结果 | 原 MOD 的权威配置后端 |
| 当前生效值 R | 原 MOD 报告的当前实际运行参数或有效状态 | 原 MOD 的运行状态 |
| 编辑草稿 D | 玩家在面板上编辑、尚未提交的意图 | 管理模块内存；不写入 TheArchive 设置文件 |
| 临时覆盖 T | 原 MOD 接受的本进程覆盖，与 P 分离 | 原 MOD 内存；退出进程后自然消失 |

R 必须来自目标 MOD 对有效状态的报告。只能读取配置、无法确认当前运行状态时，页面写“当前生效状态未知”，不能把 P 冒充 R。异步应用可以返回“等待确认”，超时后标记未确认／失败并刷新，不将成功写配置当作实际生效证明。

用户主视图优先展示当前值与编辑控件；当 P、R、D 不一致时显示“已临时应用”“未应用草稿”“已保存，待下次启动”等差异提示，避免始终显示四套数字。以下状态独立判断，可以同时存在：

- 接入状态：等待初始化／可用／未适配／版本不兼容／异常。
- 草稿状态：无编辑／有草稿／校验失败／状态冲突。
- 应用状态：已确认生效／等待安全时机／等待目标确认／未确认／部分失败。
- 保存状态：未保存／已保存／保存失败；需后续加载时另列生效时机。

权限不足、局内受限、兼容规则接管时，禁用相应操作并显示原因，不把这些状态汇总成含糊的“设置无效”。

## 3. 草稿与操作语义

进入详情页时读取 P、R、能力及版本／状态修订号，形成该页草稿基线。没有草稿时随目标状态刷新；有草稿时保留玩家编辑并检查基线是否过期。页面切换或关闭保留本进程草稿并显示待处理提示，不自动提交；退出游戏丢弃草稿。

所有操作默认以当前 MOD 的一次变更集为边界。原型不提供跨 MOD 一键操作；不同持久文件或原子性不足的设置组必须在执行前拆成可说明的独立单元，不能执行后才把部分成功显示为整体成功。

| 操作 | 具体行为 | 不支持时 |
| --- | --- | --- |
| 应用到本次游戏 | 校验本页变更集，提交给原 MOD 的临时运行接口；更新 T／R，不改变 P，不写任何配置文件 | 禁用操作并解释，例如“当前版本仅支持保存后重启” |
| 保存为默认 | 校验后只更新原 MOD 的持久配置 P；不隐式调用运行应用，保留当前 R／T；显示已保存与后续生效时机 | 只读；不能绕过原 MOD 后端直接拼写其 CFG／JSON |
| 恢复已保存设置到本次游戏 | 读取最新 P，显式提交给原 MOD，清除对应临时覆盖并确认 R；不保存、不动其他未接入项 | 对不可即时恢复项标明所需时机；无法保证清理时禁用并要求重启 |
| 放弃草稿 | D 回到最新读取基线；不更改 P、R 或已经生效的 T | 始终只作用于草稿 |

C2 基线没有默认自动执行的“应用并保存”，避免临时试调意外写入下次配置；需要两种效果时玩家分别操作。**C3 按用户要求对 `ImmediateAutoSave` 简单字段做了明确例外：控件修改后立即更新 R 并写入 P，不再显示“应用”和“保存”。** 批量/重启字段仍保留“保存更改／取消更改”或行内重启提示的语义。保存失败不能伪装成功；即时保存失败时页面必须回读原值并报告。

存在尚未处理的草稿时执行“恢复已保存设置”，先显示其将被替换的范围并要求二次操作确认。原型优先使用原生按钮／确认页，不强行挂钩游戏退出；退出进程丢弃草稿的语义在页面说明。

## 4. 应用与保存时机

| 时机 | 临时应用策略 | 保存策略 |
| --- | --- | --- |
| 即时 | 原 MOD 在游戏主线程完成验证与状态更新，读回确认 | 支持时可独立保存，保持 R 不变 |
| 下次对象创建／打开界面 | 仅原 MOD 能追踪请求、取消与完成时才允许排队，页面明确待生效 | 保存后标明下一实际加载时机 |
| 返回大厅 | 由原 MOD 判断真实游戏状态，支持受控队列时才接受临时请求；不能由面板仅凭场景名称猜测 | 持久保存不等于自动排队 |
| 下次启动 | 不接受声称本进程生效的临时操作 | 保存后提示需要完整重启 |

原型只开放即时临时应用和已证明隔离的持久保存；其他类型先显示状态或只读。后续阶段再加入安全边界队列，队列绑定目标实例、修订号、权限和本次进程，允许显式取消；过期、离开大厅身份变化或目标销毁时重新校验，不静默执行旧请求。进出关卡不自动清除本进程临时偏好，但对象绑定的请求与资源需由原 MOD 正确释放、重新绑定。

## 5. 适配边界与数据流

```text
页面控件 → 内存草稿 → 操作协调器
                         ↓
              版本／状态／权限／范围校验
                         ↓
                    显式模块适配器
                         ↓
           目标 MOD 的运行接口／权威保存后端
                         ↓
                读回状态与明确操作结果
```

操作协调器负责防重入、修订号检查、结果记录和页面刷新；适配器描述模块能力并转接调用；目标 MOD 负责游戏状态、有效值、兼容约束、线程及文件保存。接口先以本仓内部模型和受控测试定义，不新增所有 MOD 都必须引用的协议程序集。目标提供必要的小接口时保留在原仓，可用反射或隔离调用绑定，具体签名在 C2／C3 实现时冻结。

最少需要表达以下能力，名称仅是设计语义，不是已存在 API：

| 能力 | 输入／输出要点 |
| --- | --- |
| 发现与能力查询 | 模块身份、版本、初始化状态、受支持操作、生效时机与限制原因 |
| 状态读取 | P、R（或未知）、当前覆盖、配置／运行修订号与有效范围 |
| 变更验证 | 完整变更集、期望修订号；范围、枚举、跨项关系、状态及权限错误 |
| 临时应用／恢复 | 目标 MOD 更新运行快照，返回实际接受值、完成／等待状态及可恢复性 |
| 持久保存 | 原 MOD 按期望文件修订提交，返回真实保存结果；不连带写回临时覆盖 |

不把 `ConfigEntry.Value` 赋值后短暂关闭自动保存作为通用临时机制。正常退出时原 MOD 可能再次 Save，其他插件也可能保存同一配置对象；仅控制一次赋值不能证明之后不写盘。

对原本直接读取 ConfigEntry 的有源码 MOD，可能需要增加独立运行快照与临时覆盖，使“配置读取／保存”和“实际应用”解耦；持久化事件也不能偷偷更新 R。未完成这种隔离前，不开放无法兑现的操作。对冻结 DLL 先只读核验；只有其已有能力能满足语义时才开放相应操作，不改冻结基线。

## 6. 保存、冲突与失败处理

每项配置仍只有原 MOD 的权威持久来源。管理模块可单独保存自己的页面偏好，但不得持久化目标 P 的镜像、D 或 T。TheArchive 特性配置序列化必须避开这些对象；在 C1／C4 检查所有相关写盘路径，必要时使用不保存的页面数据与操作按钮，不将框架自动保存当作目标保存实现。

持久保存通过原 MOD 后端执行，保留未接入键、未知项、同文件其他模块的配置和用户有效自定义。禁止用局部草稿替换整个共享 ConfigFile。文件写入应使用同目录临时文件与可靠替换／回退方式；失败保留原文件，清理已验证的临时文件，不制造半写入文件。不能满足这些条件的后端暂不开放保存。

共享文件按真实文件而非页面设互斥与修订检查，例如多个模块共用一份配置时必须由同一后端协调。写入前比较文件版本／内容指纹及运行修订；外部编辑、热键、其他插件或另一页面改变状态时，停止过期提交，保留草稿并提示刷新后重新确认。首版不提供强制覆盖或自动合并冲突；读取非法文件时保留原件，不用默认值覆盖损坏内容。

每次操作重新验证权限与目标生命周期。单模块内能原子更新时才承诺整组成功；发生部分失败时尽力恢复并读回校验，恢复未确认则显示“状态未确认／需要重启”，暂停该模块后续写操作。不能用全局 Unpatch、禁用其他插件或重载 DLL 作为回滚。

返回结果至少区分：成功、等待、校验拒绝、权限拒绝、状态冲突、应用失败、保存失败、恢复失败、目标不可用。页面显示用户可执行的下一步，日志保存必要细节；不因单模块异常阻断其他页面。

## 7. 临时生命周期与独立运行

临时设置默认持续到游戏进程结束，可跨关卡；原 MOD 对对象绑定状态负责，不把 T 写入持久配置。需要会话清理的值由所属 MOD 在正确生命周期处理，面板不持有失效 Unity 对象。

菜单关闭不撤销临时值；退出进程后下次启动按 P 初始化。修改／移除 DLL 均要求退出游戏后进行。游戏退出时不要求先把内存临时值写回原配置再覆盖回来，因此异常退出也不应污染持久值。

各原 MOD 无管理模块时继续走其原配置与原操作入口。框架或管理模块不兼容时停止管理能力；涉及目标 MOD 接口改动的版本须单独验证它在未安装本管理模块时的独立运行。联机写入由目标原有权威侧处理，面板不新增全局网络同步；不具备权限或同步依据的共享玩法设置先只读。

## 8. 首版范围与后续扩展

首个原型选一个有源码、影响本地表现、可观察且可恢复的目标模块，具体模块与配置项在 C3 前选择，不自动纳入全部现有 CFG。C3 实际采用“简单字段即时写 P＋R”，因此原“临时值与 P 严格分离、保存不隐式应用”的验收条款不再适用于这 8 个字段。C4 已补齐安全行级保存、未知键/注释保留、写入失败回滚、重启读回和目标缺失隔离；共享文件保护对独立 ConfigFile 不适用，明确留 C5。C3 不以恢复默认或批量保存作为完成条件。

全局应用、配置预设／导入导出、批量恢复默认、网络配置分发、自动安装更新、冻结 DLL 行为修改不在首个原型范围。后续新增功能需明确其状态和失败语义，不能直接沿用普通设置控件的自动赋值行为。

## 9. C1/C2/C3 实现接线备注

本节记录 C1/C2/C3 落地时与本机 TheArchive `0.0.838` 相关的接线事实，不改变上面的设计语义；框架升级后仍需重新核验。

- **双入口避免**：本程序集由 BepInEx 以 `[BepInPlugin]` 加载，同时由 `Plugin.Load()` 调用 `ArchiveMod.RegisterArchiveModule` 注册一个不带 `[ArchiveModule]` 的 `IArchiveModule` 类型。TheArchive 的 Chainloader 会递归扫描插件目录并实例化带该特性的类型；若本程序集同时带特性，会产生第二个模块实例。`Build.ps1` 对成品执行“无 `[ArchiveModule]`”守卫。
- **Feature 可实例化**：TheArchive 在模块注册时会枚举程序集中的每个 `Feature` 子类并尝试实例化，不跳过抽象类型；因此本仓不保留抽象的 `Feature` 基类，页面共享逻辑放在静态辅助类中。`Build.ps1` 同时检查成品不存在抽象或开放泛型的 `Feature` 子类。
- **模块分组名**：`设置 → 模组设置 → PreLuna` 的显示名与描述来自随 DLL 安装的 `Definitions/Module_PreLuna.ModControl_Group_Definition.json`；该文件是 TheArchive 原生模块定义数据，不由管理模块写入。
- **设置属性**：每个页面的静态 `Settings` 属性必须带 `[FeatureConfig]`，且具有 public static 的 get／set；否则 TheArchive 不会创建设置子菜单，页面只显示功能行和描述。C1 实机首轮曾因缺少该特性只看到三个启用行，已补齐并加入 `Build.ps1` 守卫。
- **只读页面**：C1 概览、已接入 MOD、状态与诊断仅使用 `FLabel`／`FButton`（`NotSavedFeatureSetting` 组件），不提供可编辑 `FeatureSetting`，因此不会建立目标配置或草稿文件；刷新按钮只重新读取内存中的框架／插件状态。
- **显示位置**：TheArchive 原生结构为左侧功能列表＋“设置 → 进入”子菜单，右侧为功能描述。C1 把状态项、已加载插件列表和刷新按钮放在左侧设置子菜单；右侧只保留简短说明。`FLabel` 本身是单行设置行，不能承载 `\n` 多行文本，因此概览/诊断拆成逐行 `FLabel`，已接入 MOD 每个插件一行（C1 最多 24 行，超出显示汇总；后续改为动态/分页）。后续可编辑控件继续使用该左侧子菜单，避免把只读内容先放右侧、后续再迁移。
- **刷新按钮置顶**：三个页面的 `Refresh` 属性声明在每个 Settings 类最前面，使 TheArchive 按属性声明顺序把它放在设置行最上方；不要运行时清空/重排 `FeatureSettingsHelper.Settings`，配置加载会恢复声明顺序，清空还可能丢失行。已接入 MOD 列表可能很长，按钮不能沉到页尾。刷新只重读内存状态，不写盘。
- **多行列表实现**：已接入 MOD 使用固定 24 个 `FLabel` 行，刷新时把未使用的 `LabelSetting` 从 `FeatureSettingsHelper.Settings` 移除，只保留已加载目标；不写盘、不改目标配置。
- **目标发现**：只列出 BepInEx 已加载的 `PreLuna.*` 插件并排除本模块自身；不静态引用目标程序集，不扫描未加载插件。
- **当前操作模型（C4 清理后）**：`ModControl/src/Core/Operations` 只保留 `OperationCoordinator.SetImmediate`、`TargetSnapshot`（P/R）、`SettingDefinition`/`SettingValue`、能力/权限、修订检查与 `ChangeSet`。`FakeTargetProvider` 只模拟读取、校验、写入、冲突、失败和重入；C3 通过 `EnemyHealthBarAdapter` 接真实目标。初版 C2 的 Draft、Apply/ Save/ Restore、Deferred/Restart 已删除，仅保留为历史设计。
